# 生产环境升级到 v1.0.x（开源去客户端化）

适用对象：已在运行的生产实例（bf.imask.cc）。本文档假设生产由旧版一键脚本安装，目录为 `/opt/backup-center`。

> **2026-10-12 已实际执行完毕**（v1.0.2）。文末「实战记录」一节补充了真实踩到的坑与本文档的修正点，动手前先看那一节。

> **与开源版新装实例的区别**：新装实例目录是 `/opt/bc`，生产是 `/opt/backup-center`。所有命令用 `$BC_DIR` 变量，先按第 0 步确认再执行。

---

## 一、升级会带来什么变化

| 项目 | 变化 |
|---|---|
| `client_centers` 表 | **删除** |
| `system_settings` 中 5 个键 | **删除**：`is_master` / `master_upstream_url` / `master_push_token` / `pending_agent_update` / `pending_center_update` |
| 3 条无鉴权接口 | **下线**：`/api/master/notify`、`/api/master/notify-center`、`/api/client/self-register` |
| 前端「客户端」「主控推送」设置页 | **下线** |
| 资源池 / 资源库 | **不再受 `is_master` 门控**，所有登录账号可见 |
| 新增 `/api/auth/bootstrap` | 已有管理员时自动关闭，**不影响现有登录** |
| 业务数据 | servers / websites / storages / backup_logs **全部保留** |

---

## 二、⚠️ 动手前必读的三条

1. **`deploy/.env` 里的 `APP_KEY` 绝对不能变。** 数据库里所有 rclone 存储凭证是用它加密的，一旦重新生成，全部存储密码解不开 → 所有备份任务失败。本次升级**不要**执行任何会重写 `.env` 的操作（旧版 install.sh 的"生成新 APP_KEY"步骤尤其不能跑）。
2. **如果还有下游"客户端 Center"在向本实例注册或拉更新，升级后它们会失联。** 这是预期效果，但请确认你不再需要管理它们。
3. **迁移不可逆。** `client_centers` 表删了就没了。所以第 1 步的备份必须做，且备份完成前不要往下走。

## 第 0 步 · 确认环境（先跑，别猜）

```bash
# 确认安装目录
sudo ls -d /opt/bc /opt/backup-center 2>/dev/null

# 确认容器状态
sudo docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Image}}'

# 确认卷名
sudo docker volume ls | grep -i bc
```

按实际结果设置变量（后续命令都依赖它）：

```bash
export BC_DIR=/opt/backup-center     # 如果上一步显示是 /opt/bc 就改这里
sudo ls -la $BC_DIR/deploy/
```

**预期能看到**：`docker-compose.yml`、`.env`、`nginx.conf`、`ssl/`、`frontend-dist/`、`agent-dist/`。
如果 `frontend-dist` 或 `agent-dist` 缺失，记下来，第 3 步处理方式不同。

---

## 第 1 步 · 备份（3 样，缺一不可）

```bash
# 1) 数据库（最关键的资产）
sudo docker cp bc-app:/var/www/html/database/data/database.sqlite \
    /root/database-$(date +%Y%m%d-%H%M).sqlite.bak

# 2) APP_KEY
sudo cp $BC_DIR/deploy/.env /root/deploy-env-$(date +%Y%m%d-%H%M).bak

# 3) SSL 证书
sudo tar -czf /root/ssl-$(date +%Y%m%d-%H%M).tar.gz -C $BC_DIR/deploy ssl

# 校验备份确实有内容
sudo ls -lh /root/*.bak /root/ssl-*.tar.gz
```

> 若 `docker cp` 的路径不存在，先确认真实库路径：
> `sudo docker exec bc-app php artisan tinker --execute='echo config("database.connections.sqlite.database");'`

## 第 2 步 · 下载新版本到临时目录（**不要**直接解到生产目录）

```bash
curl -fsSL -o /tmp/bc-new.tar.gz \
    https://github.com/gongpz/backup-center/releases/latest/download/bc-deploy.tar.gz

mkdir -p /tmp/bc-new && tar -xzf /tmp/bc-new.tar.gz -C /tmp/bc-new
ls /tmp/bc-new            # 应看到 backend/ 和 deploy/ 两个目录
```

## 第 3 步 · 精确覆盖代码

**这一步是重点：不能整目录覆盖 `deploy/`**，否则会把 `.env`、`ssl/`、`nginx.conf`、`docker-compose.yml` 一起冲掉。

### 3.1 保留不动的文件（生产特有的配置）

| 文件 | 为什么不能覆盖 |
|---|---|
| `deploy/.env` | 存着 `APP_KEY`，覆盖 = 存储密码全废 |
| `deploy/nginx.conf` | 含生产域名 `bf.imask.cc` 与证书路径，新包里是 `server_name _` 模板 |
| `deploy/docker-compose.yml` | 生产的版本挂着 `/opt/backup-center/agent-dist` 绝对路径 + `APP_URL=https://bf.imask.cc`；新包里改成了相对路径 `./agent-dist`，直接覆盖会让 Agent 下载目录指向错误位置 |
| `deploy/ssl/` | Let's Encrypt 证书 |
| `deploy/agent-dist/` | 你正在分发给 Agent 的二进制（新包里也有，但版本一致，没必要动） |

### 3.2 执行覆盖

```bash
# ① 后端源码整体替换
sudo rm -rf $BC_DIR/backend
sudo cp -a /tmp/bc-new/backend $BC_DIR/backend

# ② 前端产物整体替换（前端是预构建的 dist，服务器上不需要 Node）
sudo rm -rf $BC_DIR/deploy/frontend-dist
sudo cp -a /tmp/bc-new/deploy/frontend-dist $BC_DIR/deploy/frontend-dist

# ③ 补齐 nginx 模板（缺这两个文件是历史 R93b 事故的根因）
sudo cp -n /tmp/bc-new/deploy/nginx.http.conf  $BC_DIR/deploy/ 2>/dev/null || true
sudo cp -n /tmp/bc-new/deploy/nginx.https.conf $BC_DIR/deploy/ 2>/dev/null || true

# ④ 删除主控/客户端残留文件（覆盖不会自动删掉旧文件，必须手工清理）
sudo rm -f $BC_DIR/backend/app/Http/Controllers/Api/ClientCenterController.php \
          $BC_DIR/backend/app/Http/Controllers/Api/MasterNotifyController.php \
          $BC_DIR/backend/app/Models/ClientCenter.php \
          $BC_DIR/backend/database/migrations/2026_08_10_010000_create_client_centers_table.php \
          $BC_DIR/backend/app/Console/Commands/InstallerSyncCommand.php
```

### 3.3 清理推送升级的历史残留（可选但建议）

```bash
sudo rm -rf $BC_DIR/.control
sudo systemctl disable --now bc-update.timer 2>/dev/null || echo "（无 update.timer，忽略）"
```

## 第 4 步 · 重建镜像并启动

```bash
cd $BC_DIR/deploy
sudo docker compose build app
sudo docker compose up -d --force-recreate app
sudo docker compose ps
```

> 只重建 `app` 即可；`web`（nginx）挂的是目录卷，前端产物已直接替换，无需重建。

---

## 第 5 步 · 执行迁移 + 清缓存

```bash
# 迁移（production 环境必须加 --force，否则会卡在确认提示）
sudo docker exec bc-app php artisan migrate --force

# 清缓存（旧配置/旧路由缓存不清会导致 500）
sudo docker exec bc-app php artisan optimize:clear
```

**预期输出**：
```
2026_10_12_000001_drop_client_centers_and_master_settings ......... 5ms DONE
```

## 第 7 步 · 回滚方案

只有在第 6 步出现不可接受的问题时才回滚，且**代码和数据库必须一起回滚**（表已经删了）。

```bash
cd $BC_DIR/deploy
sudo docker compose down

# 恢复数据库
sudo docker cp /root/database-XXXX.sqlite.bak bc-app-tmp:/tmp/ 2>/dev/null || true
# 更稳妥：再加一份卷内副本（生产卷名是 deploy_bc-database）
sudo docker run --rm -v deploy_bc-database:/data -v /root:/host alpine \
    cp /data/database.sqlite /host/bc-db-vol-$(date +%Y%m%d-%H%M).sqlite

# 恢复旧代码：如果你有上一版部署包
sudo rm -rf $BC_DIR/backend
sudo tar -xzf /root/旧版bc-deploy.tar.gz -C $BC_DIR

sudo docker compose build app && sudo docker compose up -d
```

> 如果没有保留上一版部署包，回滚这条路基本走不通 —— 这就是为什么第 1 步的备份必须先做。

## 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `migrate` 报 `no such table: client_centers` | 迁移已用 `dropIfExists`，正常不会报。若报了，说明 sqlite 版本异常，可手工跳过：`docker exec bc-app php artisan migrate --force --path=其他迁移` |
| 登录后 500 | `optimize:clear` 没执行，重跑一次 |
| 页面还是旧样子 | 浏览器硬刷新（Ctrl+F5）；确认 `$BC_DIR/deploy/frontend-dist/index.html` 时间戳是刚才 |
| 所有备份任务失败、`rclone` 报解密失败 | **APP_KEY 被改了** —— 立刻用第 1 步的 `.env` 备份恢复 |
| Agent 下载二进制 404 | 检查 `deploy/agent-dist/` 是否还在，`docker-compose.yml` 没被覆盖 |

## 实战记录（2026-10-12 执行时踩到的坑）

以下都是文档初版没写、实际执行时才暴露的问题，已按此修正流程。

### 1. 无 swap，构建会失败

生产 VPS 只有 **964 MB 内存且 swap 为 0**。`composer install` / `dump-autoload` 阶段有 OOM 风险。先加：

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
grep -q '/swapfile' /etc/fstab || echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

### 2. 部署包缺 `bootstrap/cache` → 镜像构建失败（v1.0.1 的 bug）

报错：
```
Script @php artisan package:discover --ansi handling the post-autoload-dump event returned with error code 1
```

原因链：**Git 不跟踪空目录** → `backend/bootstrap/cache/` 在本地是空目录，从未入库 → 打包出来的部署包里没有这个目录 → `composer dump-autoload` 触发的 `package:discover` 无法写入 `bootstrap/cache/packages.php` → 构建中断。旧的生产部署包里该目录带 `.gitignore` 所以一直没暴露。

已修（v1.0.2）：补 `backend/bootstrap/cache/.gitignore`，并把 Dockerfile 里的 `mkdir` 移到 `dump-autoload` **之前**，不再依赖源码自带目录。

### 3. 顺序：先构建成功，再换前端

第一版流程先换了 frontend-dist 再构建，构建失败后现场变成**新前端 + 旧后端**——新登录页去请求 `/api/auth/bootstrap-status`，旧后端没有这个路由，直接 404。

正确顺序：换 backend → 构建 → 构建成功 → 重建容器 → **最后**换 frontend-dist。

### 4. 迁移会自动执行，不用手动

`docker-entrypoint.sh` 启动时会跑 `php artisan migrate --force`。所以手动执行经常看到 `Nothing to migrate` —— 不代表没迁移，用查询结果判断（见第 6 步）。

### 5. 生产热补丁：Agent 版本号

生产曾手工把 `config/agent.php` 的 `latest_version` 从 `0.13.0` 改成 `0.14.0`（与 agent-dist 里的二进制对齐），仓库里没有。直接覆盖会丢这个补丁，导致 Center 报告的版本低于 Agent 实际版本，**Agent 反复触发升级**。已同步回仓库。

> 教训：升级前先 diff 生产 `backend/` 与仓库，别假设服务器和代码库一致。

### 6. 必须停掉的推送定时器

生产上 `bc-update.timer` **每 60 秒**跑一次 `/opt/backup-center/update-runner.sh`（主控推送升级用）。升级前必须先停，升级后删除：

```bash
systemctl disable --now bc-update.timer
rm -f /opt/backup-center/update-runner.sh /etc/systemd/system/bc-update.{service,timer}
systemctl daemon-reload
```

### 7. 卷名是 `deploy_bc-database`

compose 项目名取自 `docker-compose.yml` 所在目录名 —— 生产是 `deploy/`，所以卷名前缀是 `deploy_`，不是 `bc_`。
